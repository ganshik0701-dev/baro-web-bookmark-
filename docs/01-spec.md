# 01. 기능·화면 명세

우선순위: P0 = MVP 필수, P1 = v1.1, P2 = v2.0. 총 9개 영역 42개.

## 배경: 북마크를 가져오는 방법

Google 로그인만으로는 크롬 북마크를 읽을 수 없다(공개 API 없음, Google Bookmarks는 2021년 종료). 그래서:

1. **앱이 로컬 파일을 직접 읽는다** — `%LOCALAPPDATA%\Google\Chrome\User Data\<프로필>\Bookmarks` (JSON)
   - 구조: `roots.bookmark_bar`, `roots.other`, `roots.synced` 아래 `type: folder` / `type: url` 트리
   - 각 항목에 `id`, `name`, `url`, `date_added`
   - `date_added`는 1601년 기준 마이크로초 → 유닉스 초 = `값 / 1000000 - 11644473600`
   - 파싱 실패 시(크롬이 저장 중) 1초 뒤 1회 재시도
2. **확장이 실시간 변경을 보낸다** — `chrome.bookmarks` 이벤트
3. **HTML 업로드** — 크롬 '북마크 내보내기' 파일 (예비 수단)

세 경로 모두 서버의 `POST /sync/chrome` 또는 `POST /import/chrome`으로 모인다. 동기화는 크롬 → 바로 한 방향이다.

### Bookmarks 파일 읽기 규칙 (DESK-01)

파일 읽기·파싱은 **메인 프로세스에서만** 한다. 렌더러에는 preload로 결과만 넘긴다(읽기 함수 자체를 노출하지 않는다).
크롬 `Bookmarks` 파일은 **읽기 전용**으로만 다룬다(`readFile`·`stat`만 쓴다).

**프로필 탐색**: `%LOCALAPPDATA%\Google\Chrome\User Data\` 아래 `Default`·`Profile 1`·`Profile 2`… 중 `Bookmarks` 파일이 있는 폴더만 후보로 모은다. 서버로 보내는 `profile`은 폴더 이름(`"Default"`)이다.

**표시 이름과 자동 선택 (DESK-02)**: 같은 폴더의 `Local State`(JSON, 읽기 전용)에서 `profile.info_cache[폴더명].name`을 표시 이름으로, `profile.last_used`를 마지막으로 쓴 프로필로 읽는다. 이 파일이 없거나 깨져도 **오류로 보지 않는다**(표시 이름 없이 폴더명만 쓴다). 이메일(`user_name`)은 읽지 않는다. `info_cache`에 있어도 `Bookmarks` 파일이 없는 프로필은 목록에서 뺀다.

고를 순서는 ①이 PC에 저장해 둔 선택 ②서버 `GET /me`의 `chromeProfile` ③`Local State`의 `last_used` ④`Default` ⑤`Bookmarks` 수정 시각이 최근인 것. 다섯 중 **파일이 실제로 있는 것**만 고르고, 저장해 둔 프로필이 사라졌으면 조용히 다음으로 내려간다. 서버의 `profiles.chrome_profile`은 동기화(DESK-03)가 `profile` 필드로 갱신한다.

**파일 직접 선택**: 기본 경로에서 못 찾으면 메인 프로세스가 `dialog.showOpenDialog`로 파일을 고르게 한다. 고른 파일도 같은 읽기 규칙(50MB 상한·JSON·`roots` 검사)을 지나야 선택으로 저장한다. 크롬 파일이 아니면 `no_roots`로 거절한다.

**렌더러에 노출하는 함수 (preload)**: `listChromeProfiles()`·`pickChromeBookmarksFile()`·`readChromeBookmarks()`·`getChromeSelection()`은 **인자를 받지 않고**, `selectChromeProfile(name)`은 탐색 목록에 있는 폴더명일 때만 받는다. 경로를 인자로 받는 읽기 함수는 만들지 않는다(렌더러가 임의의 파일을 읽게 되므로). 경로는 화면에 보여주기 위해 결과에 담아 내보내기만 하고, 렌더러가 돌려보내는 경로는 쓰지 않는다.

### 동기화 실행 규칙 (DESK-03)

**토큰**: 메인 프로세스가 `Authorization: Bearer <액세스 토큰>`을 붙여 `POST /sync/chrome`을 부른다. 토큰은 `auth.ts` 밖으로 값이 나가지 않고, 호출 직전에 "유효한 토큰을 보장하는 함수"로만 얻는다(만료 5분 전이면 그 함수가 먼저 갱신한다). 갱신 요청은 리프레시 토큰 rotation 때문에 한 번에 하나만 나간다.

**401 재시도**: 서버가 `401`을 주면 한 번 더 갱신해 **딱 1회만** 다시 보낸다. 두 번째도 실패하면 '로그인이 만료됐습니다'로 끝낸다. `400`·`409`·`413`·`429`·`5xx`는 재시도하지 않는다(동기화 본문이 최대 2MB라 함부로 다시 보내지 않는다).

**보내지 않는 경우**: 파싱 실패(`read_error`·`invalid_json`·`no_roots`·`bad_root`·`too_large`)면 자동·수동 모두 보내지 않는다. `suspicious`(북마크 0개)면 자동 동기화는 보내지 않고, 수동일 때만 "크롬에서 북마크를 찾지 못했습니다. 계속하면 바로의 동기화 북마크가 모두 지워질 수 있습니다"를 확인받고 보낸다.

**대량 삭제 확인**: `409 MASS_DELETE_CONFIRM_REQUIRED`는 **아무것도 반영되지 않은 상태**다. 삭제 예정 수와 미리보기(최대 5개)를 보여주고 확인받는다. 확인은 렌더러 모달(SCR-02)로 받는다. 메인은 상태를 `needs_confirm`으로 바꾸고 렌더러의 답(`true`/`false`)만 기다린다. 창이 닫히면 취소로 본다(메인이 영원히 기다리지 않게).
- 확인하면 **파일을 새로 읽지 않고 같은 요청 그대로** `confirmDeleteCount: <보여준 수>`만 붙여 다시 보낸다. 사용자가 본 숫자와 실제로 지워지는 숫자를 같게 하기 위해서다(확장 EXT-03은 서비스 워커라 새로 읽는다 — 여기가 다르다)
- `confirmDeleteCount`는 **메인 프로세스가 409에서 받은 값을 들고 있다가 붙인다**. 렌더러는 '확인했다'만 알린다(렌더러가 숫자를 정하면 사용자가 본 것과 다른 값이 갈 수 있다)
- 확인하는 사이 크롬에서 더 지워도 요청은 옛 스냅샷이라 삭제 수가 그대로다. 반대로 그 사이 확장이 북마크를 추가하면 삭제 대상이 늘어 **다시 409**가 온다. 그때는 새 숫자로 다시 묻는다(자동으로 반복 확인하지 않는다)
- 취소하면 아무 요청도 보내지 않고 다음 동기화에서 다시 묻는다

**자동 동기화**: 앱 시작 시 1회만 한다(주기적 동기화를 두지 않는다). 사용자가 '지금 동기화'를 연타해도 요청은 하나만 나간다.
**단, 첫 동기화 전(`GET /me`의 `lastSyncedAt`이 `null`)에는 자동으로 보내지 않는다.** 대신 SCR-02를 띄워 사용자가 프로필을 고르고 '가져오기'를 누르게 한다. 자동으로 먼저 보내 버리면 프로필이 여러 개인 PC에서 고를 기회 없이 엉뚱한 프로필이 올라간다.

**v1 한계 — 앱과 확장이 겹칠 때**: 서버는 `profiles` 행을 잠가 한 번에 하나씩 처리하지만, 앱이 파일을 읽은 뒤 전송 전에 확장이 새 북마크를 보내면 그 북마크는 앱의 `full` 스냅샷에 없어 **삭제 대상이 된다**. 앱은 파일을 읽고 바로 보내 이 간격을 줄이고, 큰 삭제는 409가 막는다. 그래도 1~19개 규모는 조용히 지워질 수 있고, 북마크는 다음 동기화에서 돌아오지만 **방문 기록은 돌아오지 않는다**. 서버가 방금 들어온 `ext_sync` 항목을 삭제에서 지켜 주는 방식은 v1.1 후보다.

**프로필 교체**: 서버 `chromeProfile`과 이번에 보내려는 프로필이 다르면 `full`이 프로필 교체가 되어 이전 프로필분이 모두 삭제 대상이 된다(docs/03-api.md 'v1 한계'). 이때는 보내기 전에 먼저 알리고, 대량이면 409 확인도 거친다.

**요청 변환**: 확장과 같은 결과를 만든다(docs/01-spec.md '확장 동작 규칙'의 '북마크 → 요청 변환'과 같은 규칙).
- `roots.bookmark_bar`(id `1`)·`roots.other`(`2`)·`roots.synced`(`3`)은 folders에 넣지 않는다. 그 아래 폴더만 넣는다
- 파일에는 부모 id가 없다(중첩 구조). 순회하면서 부모의 `id`를 `parentChromeId`로 채운다
- 최상위 폴더 바로 아래 북마크는 `parentChromeId`가 `1`·`2`·`3`이라 서버가 미분류로 둔다
- http/https가 아니거나 2048자를 넘는 URL은 빼고 개수만 센다(`packages/shared`의 `httpUrl`)
- 제목은 그대로 보낸다(100자 자르기는 서버가 한다)

**`date_added` 변환**: 1601년 기준 마이크로초 문자열 → `BigInt(값) / 1000n`으로 밀리초를 만든 뒤 `11644473600000`을 뺀다. 실제 값이 17자리라 `Number`로 먼저 바꾸면 정밀도를 잃으므로 반드시 `BigInt`로 나눈 뒤에 `Number`로 바꾼다. 숫자가 아니거나 `"0"`, 1970년 이전, 하루 넘게 미래면 `addedAt`을 **넣지 않는다**(서버에서 선택 항목).

**실패와 재시도**: 아래는 파싱 실패로 보고 `full`을 보내지 않는다.

| 사유 | 상황 | 1초 뒤 1회 재시도 |
| --- | --- | --- |
| `read_error` | 파일 없음·권한·`EBUSY`(크롬이 저장 중) | ○ |
| `invalid_json` | JSON이 깨짐(저장 중이라 잘린 파일) | ○ |
| `no_roots` | `roots`가 없거나 객체가 아님, 알려진 루트가 하나도 없음 | ○ |
| `bad_root` | 루트의 `children`이 배열이 아님 | ✗ |
| `too_large` | 파일이 50MB를 넘음(읽기 전에 `stat`으로 막는다) | ✗ |

항목 하나가 이상하면(`type`이 없는 등) 그 항목만 건너뛰고 나머지는 계속 읽는다.

**의심스러운 결과**: 파싱은 성공했는데 북마크가 0개면 `suspicious: true`를 함께 돌려준다. 파일이 반쯤 읽혔거나 프로필을 잘못 고른 경우일 수 있어서, DESK-03은 이때 `full`을 그냥 보내지 않고 사용자에게 확인받는다. 북마크가 정말 없는 새 프로필도 있으므로 파싱 자체를 실패로 보지는 않는다.

### 확장 동작 규칙 (EXT-01~04)

**구조**: Manifest V3. 권한은 `bookmarks`·`storage`만, `host_permissions`는 운영 API(`https://baro-web-bookmark-api.vercel.app/*`)와 로컬 개발 서버(`http://localhost:3000/*`)만. manifest `key`로 확장 ID 고정(개발자 모드 설치). content script 없음.
- 모든 `fetch`와 `chrome.bookmarks` 읽기는 **서비스 워커에서만** 한다. 팝업은 메시지만 보내고 `chrome.storage.local`의 상태를 읽어 그린다(팝업을 닫았다 열어도 복원)
- 토큰은 `chrome.storage.local`에만 저장한다(`storage.sync`·`storage.session` 쓰지 않음). 팝업 입력창은 가림 처리, 저장 후엔 끝 4자리만 표시(팝업은 원본을 읽지 않고 서비스 워커가 끝 4자리만 상태에 넣는다). 토큰은 콘솔·오류 메시지에 절대 싣지 않는다
- 연결 상태: `GET /me`로 확인. `연결됨` / `토큰 무효`(401) / `서버 연결 실패`(네트워크 오류) / `서버 오류`(그 밖)
- 동기화 상태(`idle` / `syncing` / `needs_confirm` / `done` / `error`)를 storage에 저장한다. 서비스 워커가 다시 시작됐을 때 `syncing`이 남아 있으면(진행 중이던 요청은 이미 사라짐) `error`(중단됨)로 바꾼다

**북마크 → 요청 변환** (docs/03-api.md `/sync/chrome`)
- `getTree()`의 맨 위 노드(id `0`)와 그 바로 아래 최상위 폴더(북마크바·기타 북마크·모바일 북마크)는 folders에 넣지 않는다. 그 아래 폴더는 전부 folders로, 서버가 경로 이름 그룹(`상위/하위`, 30자 초과는 끝을 살림)을 만든다. 최상위 폴더 바로 아래 북마크는 미분류
- http/https가 아닌 URL(`javascript:` 북마클릿, `chrome://`, `file://` 등)과 2048자 넘는 URL은 **보내기 전에 걸러내고** 걸러낸 개수를 결과에 보여준다(서버와 같은 규칙: `packages/shared`의 `httpUrl`)
- `source`는 항상 `extension`. `profile`은 보내지 않는다(확장은 프로필 이름을 알 수 없음. v1은 사용자당 크롬 프로필 하나)
- 보내기 전에 JSON 바이트 크기를 재서 2MB를 넘으면 보내지 않고 안내한다(서버 413도 같은 안내). 북마크가 5,000개를 넘어도 보내지 않고 안내한다

**전체 동기화(EXT-03)와 409 확인**
- 팝업의 '전체 동기화' → 서비스 워커가 트리를 읽어 `full` 전송
- `409 MASS_DELETE_CONFIRM_REQUIRED`면 `needs_confirm`으로 바꾸고 삭제 예정 수·기존 수·미리보기(최대 5개)를 보여준다
- 확인하면 **북마크를 새로 읽어** `confirmDeleteCount: <보여준 삭제 예정 수>`를 붙여 보낸다. 다시 409면(확인하는 사이 더 지운 경우) 새 숫자로 다시 확인받는다. 자동으로 반복 확인하지 않는다
- 취소하면 아무 요청도 보내지 않고, '전체 동기화 필요' 표시를 남긴다

**실시간 동기화(EXT-02)**
- `onCreated`·`onChanged`·`onMoved`·`onRemoved`를 1초 동안 모아 `partial` 한 번으로 보낸다(대기열은 storage에 저장해 서비스 워커가 꺼져도 잃지 않는다)
- 폴더 이름 변경·이동은 그 폴더의 하위 트리를 함께 보낸다(하위 그룹 이름이 경로라서). 삭제는 `onRemoved`의 노드와 하위 id 전부를 `deletedChromeIds`로
- 전체 동기화가 `syncing`·`needs_confirm`인 동안은 보내지 않는다(곧 보낼 전체 동기화가 담는다). 이때 생긴 변경은 버리고 '전체 동기화 필요'로 표시한다
- 크롬 북마크 가져오기(`onImportBegan`~`onImportEnded`) 중의 이벤트는 모으지 않고, 끝나면 전체 동기화를 한 번 한다
- 토큰이 없으면 아무것도 보내지 않는다

### 메인 그리드 규칙 (SCR-03)

배치(창 너비별 열·아이콘 크기)는 docs/04-design.md '그리드'.

**이번 구성(6주차)**: 시안 중 지금 기능이 있는 것만 둔다.
- 상단바: [검색창(남는 폭 전부)] [동기화] [북마크 추가] [계정]. 검색창은 SEARCH-01(아래 '검색 규칙'), 동기화는 DESK-03 `syncNow`, 북마크 추가는 SCR-04. 정렬 선택(SEARCH-04)은 검색창과 동기화 사이에, 그룹 탭(GROUP-02, P1)은 해당 기능 때 붙인다
- 계정 버튼: 이메일 첫 글자. 누르면 작은 메뉴(이메일, 로그인 저장 여부, 로그아웃). SCR-05가 생기면 설정 화면으로 옮긴다
- 창틀은 Windows 기본을 쓴다(시안의 자체 제목 표시줄은 그리지 않는다). 그룹 탭 줄이 없으므로 시안에서 탭 줄 아래에 있던 구분선을 상단바 아래에 둔다
- 섹션: '고정됨'(`isPinned`, 없으면 섹션째 숨김) + 현재 정렬 이름의 섹션(지금은 `최근 추가순`). 검색 중에는 아래 섹션 이름이 '검색 결과 N개'
- 상태바: '마지막 동기화 N분 전 · 크롬 프로필 <표시 이름>'. 시각은 앱 시작 때 `GET /me`의 `lastSyncedAt`, 이후엔 성공한 동기화의 `syncedAt`(확장이 보낸 동기화도 서버 시각에 들어 있다). 토큰 갱신 실패·열기 실패 문구도 여기에. 시안의 '확장 연결됨'은 앱이 알 수 없어 두지 않는다
- 상태 문구: 불러오는 중(300ms 안에 끝나면 띄우지 않음) / 불러오지 못함 + '다시 시도' / 북마크 0개면 "아직 북마크가 없습니다" + '동기화'

**타일**: 실제 `<button>`, 라벨은 제목 한 줄 말줄임, 전체 제목과 URL은 `title` 속성으로.
- 클릭(마우스·Enter·Space) → OPEN-01: `window.baro.openExternal(url)`. 메인이 http/https만 연다
- 방문 기록(OPEN-02)·보조 메뉴(OPEN-03)·삭제(BM-05)는 아래 '열기와 보조 메뉴 규칙'

**아이콘 출처**: `iconUrl`이 있으면 그 주소, 없으면(크롬에서 동기화한 것 전부) Google 파비콘 서비스 `https://www.google.com/s2/favicons?domain=<호스트>&sz=64`. `sz`는 64로 고정한다(파비콘은 타일의 50%라 가장 커도 36px, 고해상도 화면을 감안해 64. 창 크기에 따라 바꾸면 크기를 바꿀 때마다 주소가 달라져 아이콘을 모두 다시 받는다. `/metadata`의 기본값도 64)
- 먼저 글자 타일을 그리고, 이미지가 불러와진 뒤에만 파비콘 타일로 바꾼다. 실패(`error`)이거나 Google 기본 아이콘(가로 16px 이하)이면 글자 타일 그대로. 오프라인에서도 깨진 이미지가 보이지 않는다
- 이미지는 `loading="lazy"`(화면에 보이는 것만 요청)
- 글자: 제목의 첫 글자(`Intl.Segmenter`로 한 글자 단위, 영문은 대문자). 제목이 비면 호스트 첫 글자
- 색: 호스트(소문자, 앞의 `www.` 제거)의 FNV-1a 해시 % 8 → `--tile-1~8`. 같은 도메인은 늘 같은 색
- 렌더러 CSP `img-src`는 `'self' data: https:`. SCR-04에서 `/metadata`가 사이트 자체 아이콘 주소를 주므로 https 이미지는 모두 허용한다(2026-09-26 결정). 이미지는 스크립트를 실행하지 못하고 `http:`는 막힌다. 요청은 이미 방문하는 그 사이트로 간다. `connect-src`는 그대로 좁게 둔다

**한계 — 파비콘 요청으로 도메인이 Google에 전송된다**: 그리드에 보이는 북마크마다 **도메인이 Google로 전송된다**(경로·쿼리는 보내지 않는다. Google은 요청 IP와 도메인 목록을 알 수 있다). 학습 프로젝트라 지금은 받아들인다. **배포하게 되면 다시 볼 항목**이다. 대안: 크롬 로컬 `Favicons` DB 읽기(SQLite 네이티브 모듈, 크롬이 켜져 있으면 잠김), 서버가 아이콘을 받아 저장, 설정에서 끄기.

**목록 캐시와 갱신 (TanStack Query)**: 키 `['bookmarks']`, `staleTime` 60초. 렌더러는 preload `listBookmarks()`(인자 없음)만 부르고, 메인이 `GET /bookmarks`를 호출한다(401이면 갱신 후 1회 재시도).
- 다시 불러오는 때: 동기화 성공 직후(자동·수동), 창 포커스(60초가 지났을 때만. 확장의 실시간 변경이 여기서 들어온다)
- Electron에서는 창 전환이 `visibilitychange`로 잡히지 않으므로 `window`의 `focus` 이벤트를 쓴다
- 주기적 폴링은 하지 않는다
- 로그아웃하면 캐시를 모두 비운다(다음 로그인 계정에 이전 목록이 보이지 않게)

**가상 스크롤**: 500개 초과 시. 7주차에 1,000개 측정과 함께 한다(지금 111개는 필요 없다).

### 검색 규칙 (SEARCH-01)

서버에 요청하지 않고, 이미 받아 둔 목록을 앱에서 거른다.

**검색창**: 시안 메인 보드의 검색창(돋보기 + 입력칸, 남는 폭 전부). 안내 문구 "제목이나 주소로 검색"(시안의 "(단축키 /)"는 SEARCH-03 때). 화면에 안 보이는 라벨 "북마크 검색". `type="search"`라 Chromium 기본 지우기(×)와 Esc로 지우기가 된다.

**일치 규칙**
- 비교 대상: 제목 + 주소 + 태그. 소문자로 바꾸고(`toLowerCase`) 유니코드 NFC로 맞춘다
- 주소는 원래 값과 **디코딩한 값**(`decodeURI`) 둘 다 본다(`%EC%9C%84%ED%82%A4`도 '위키'로 찾게). 디코딩에 실패하면 원래 값만
- 검색어를 공백으로 나눈 **낱말이 모두** 들어 있어야 일치(AND). `github react`는 둘 다 든 것만
- 앞뒤 공백뿐이면 검색하지 않은 것과 같다

**거르는 방식**: 목록이 바뀔 때만 북마크마다 비교할 글자를 한 번 만들어 둔다(`useMemo`). 글자를 칠 때마다는 그 글자들에 `includes`만 한다. 입력칸은 바로 바뀌고 그리드는 `useDeferredValue`로 뒤따른다. 디바운스는 쓰지 않는다(서버 요청이 없으니 기다릴 이유가 없다).

**검색 중 화면**
- 섹션은 그대로: '고정됨'(일치하는 고정만) + '검색 결과 N개'(N은 두 섹션 합). 비는 섹션은 숨긴다. 고정이 앞에 오는 규칙(BM-07)이 이어진다
- 결과 0개: 그리드 자리에 "‘<검색어>’와 맞는 북마크가 없습니다" + [검색어 지우기](보조 버튼, 누르면 검색창으로 포커스). 북마크가 아예 없을 때는 원래의 "아직 북마크가 없습니다"
- 검색어는 메모리에만 둔다. 재시작·로그아웃하면 비운다

**검색 중 다른 일**
- 목록 갱신(동기화·창 포커스): 결과는 늘 '지금 목록 × 지금 검색어'. 검색어는 그대로다
- 삭제: 지우는 중인 타일은 숨기고(숨김 → 검색 순서), 실행 취소하면 다시 보인다
- 고정·해제: 결과 안에서 '고정됨'과 '검색 결과' 사이를 오간다
- 수정: 고친 뒤 검색어와 맞지 않으면 결과에서 빠진다(규칙대로. 검색은 그대로 둔다)
- 추가: **성공하면 검색어를 비운다**(새 타일이 맨 앞에 보이게. 맞지 않는 새 북마크가 안 보여 저장이 안 된 것처럼 보이지 않게)

**키보드**: Tab 순서는 검색창 → 동기화 → 북마크 추가 → 계정 → 타일. 앱을 켤 때 자동 포커스는 하지 않고, `/` 단축키와 Enter로 첫 결과 열기는 SEARCH-03(P1) 때.

### 열기와 보조 메뉴 규칙 (OPEN-01~03, BM-05)

**방문 기록 (OPEN-02)**: 타일 클릭 → `openExternal(url)` → 성공하면 `recordVisit(id)`. 요청은 메인이 보낸다.
- `id`는 렌더러에서 오지만 주소(`/bookmarks/<id>/visit`)에 들어가므로, **메인이 uuid 형식인지 확인한 뒤에만** 요청한다(`../me` 같은 값으로 다른 경로를 부르지 못하게). 삭제·고정도 같다
- 방문 뒤 목록을 다시 불러오지 않는다. 지금 화면은 방문 수를 쓰지 않는다. '자주 방문순'(SEARCH-04, 7주차)에서 다시 정한다

**보조 메뉴 (OPEN-03)**: Electron 네이티브 메뉴(`Menu.popup`). 렌더러는 타일의 id·고정 여부·출처만 넘기고, 메인은 **고른 항목 이름만 돌려준다**(`'pin' | 'unpin' | 'edit' | 'delete' | null`). 실제 요청은 렌더러가 항목별 IPC로 한다.
- 항목: '고정' 또는 '고정 해제', '수정', 구분선, '삭제'
- 크롬에서 온 북마크(`source`가 `app_sync`·`ext_sync`)는 '수정'과 '삭제'를 **비활성**으로 두고 맨 아래에 비활성 안내 줄 "크롬에서 고치거나 지우면 다음 동기화 때 반영됩니다"를 둔다
  - 이유: 바로는 크롬 `Bookmarks` 파일을 고치지 않는다. 바로에서만 지우면 다음 동기화에 되살아나고 **방문 기록만 영구히 사라진다**. 바로에서 고친 제목·주소는 동기화(`sync-plan.ts`)가 크롬 값과 다르다고 보고 되돌린다(앱을 켤 때마다 자동 동기화)
  - 이것은 **앱 화면의 안내이지 보안 규칙이 아니다.** 서버는 출처와 관계없이 지운다(서버에서 막으면 테스트·정리와 실제로 지워야 하는 경우까지 막힌다. 자세한 이유는 docs/03-api.md `DELETE /bookmarks/:id`)
- 키보드: 타일에 포커스를 두고 Shift+F10이나 메뉴 키. 메뉴는 타일 아래에 띄운다
  - 키보드로 연 `contextmenu`에 Chromium이 주는 좌표는 **타일 한가운데**다(`button`은 -1. 2026-09-25 실제 앱에서 확인). 그대로 쓰면 메뉴가 타일을 가리므로, 렌더러는 직전 keydown(Shift+F10·ContextMenu)으로 키보드인지 알아내고 타일 왼쪽 아래 좌표를 넘긴다. 마우스(우클릭)는 좌표 없이 보내 메인이 포인터 자리에 띄운다
  - 키를 누르고 있어도 메뉴는 **한 번만** 연다. 자동 반복으로 들어온 keydown(`repeat`)은 기본 동작을 막아 `contextmenu`가 다시 생기지 않게 한다(고치기 전에는 3.4초에 27번 열렸다: 메뉴가 깜빡이고 IPC가 그만큼 오갔다)
- 상태바의 실패 문구("고정하지 못했습니다" 등)는 다음에 열기·고정이 성공하거나 삭제를 시작하면 지운다

**고정 (OPEN-03, BM-07)**: 누르면 화면에 먼저 반영하고(낙관적) `PATCH { isPinned }`. 실패하면 되돌리고 상태바에 "고정하지 못했습니다". 성공하면 응답으로 캐시의 그 항목만 바꾼다(목록을 다시 받지 않는다). 크롬 동기화는 고정을 건드리지 않는다(6주차 f에서 확인).

**삭제와 실행 취소 (BM-05)**: 누르면 타일을 바로 숨기고, 상태바에 "'<제목>'을(를) 지웠습니다" + '실행 취소'를 5초 동안 보인다. 5초가 지나면 `DELETE`를 보낸다.
- 5초 안에 목록을 다시 받아도(포커스·동기화) 지우는 중인 것은 계속 숨긴다(되살아나 보이지 않게)
- 지우는 중에 다른 것을 지우면 앞의 것은 **바로 보낸다**. 실행 취소는 늘 마지막 하나만
- 5초 안에 앱을 닫으면 보내지 않는다(지워지지 않는 쪽이 안전하다)
- `DELETE`가 실패하면 타일을 되살리고 "삭제하지 못했습니다"
- 로그아웃하면 대기 중인 삭제는 보내지 않고 버린다(캐시를 비우는 것과 같은 이유)

### 추가·수정 모달 규칙 (SCR-04, BM-01~04)

시안: 캔버스 보드 '북마크 추가·수정 (SCR-04)', '북마크 추가 · 중복 주소 (SCR-04)'. 크기·색은 docs/04-design.md.

**여는 곳**: 상단바 '북마크 추가' → 추가 모드. 보조 메뉴 '수정'(`manual`만) → 수정 모드(그 북마크 값을 채움).

**칸**: 주소, 제목(100자), 아이콘 미리보기(제목 칸 왼쪽, 그리드 타일과 같은 규칙: 파비콘 → 없으면 글자 타일). 그룹·태그는 GROUP-01·BM-08 때.
- 검증은 `packages/shared`의 `createBookmarkInput`·`updateBookmarkInput`을 그대로 쓴다(주소가 틀리면 주소 칸 아래에 스키마의 문구)
- 수정 모드는 바뀐 칸만 보낸다. 바뀐 것이 없으면 요청 없이 닫는다. 수정에서는 제목을 비울 수 없다(`updateBookmarkInput`: 1~100자)

**제목·아이콘 자동 채움 (`/metadata`)**: 주소 칸에서 **포커스가 빠질 때만** 부른다(입력할 때마다 부르지 않는다. 사용자당 분당 20회 제한도 있다).
- 주소가 `httpUrl`을 통과하고, 마지막으로 가져온 주소와 다를 때만 부른다
- 응답이 왔을 때 주소가 이미 바뀌었으면 그 결과는 버린다
- 제목은 **제목 칸이 비어 있을 때만** 채운다(사용자가 쓴 제목을 덮어쓰지 않는다). 아이콘은 늘 새 결과로 바꾼다
- 가져오는 동안 제목 칸 아래에 "제목을 가져오는 중…". 실패(400·422·시간 초과)는 알리지 않는다. 빈 제목으로 저장하면 서버가 도메인을 쓴다(BM-01)
- 가져오는 중에 저장하면 그 결과를 기다렸다가(서버 제한 3초) 저장한다. 주소 칸에서 바로 Enter를 눌러 아직 가져오지 않았으면 그때 가져온다
- 미리보기 아이콘은 입력할 때마다가 아니라 포커스가 빠져 주소가 정해진 뒤에 바꾼다(글자마다 바꾸면 파비콘 요청이 글자 수만큼 나간다). 사이트 아이콘도 그리드와 같이 16px 이하면 글자 타일
- 요청은 메인이 한다. preload는 `fetchMetadata(url)`만 노출하고, 메인이 `httpUrl`로 다시 검사한다
- 수정 모드는 주소를 바꿨을 때만 부른다

**중복 (409 `DUPLICATE_URL`)**: 두 번째 창을 띄우지 않고 같은 모달 아래쪽을 바꾼다. 구분선 아래에 "**이미 저장된 주소입니다** · '<기존 제목>'", 버튼은 [취소] [기존 북마크 수정] [기존 북마크 열기].
- 열기: 기본 브라우저로 열고 방문을 기록한 뒤(OPEN-02와 같다) 모달을 닫는다
- 수정: 그 북마크의 수정 모드로 바꾼다(입력하던 값은 버린다)
- 기존 북마크가 크롬에서 온 것이면 '기존 북마크 수정'은 비활성이고 "크롬에서 온 북마크라 여기서 고칠 수 없습니다. 크롬에서 고치면 다음 동기화 때 반영됩니다"를 덧붙인다
- 기존 북마크를 캐시에서 못 찾으면(다른 기기에서 막 추가 등) 목록을 다시 받아 찾는다. 그래도 없으면 '이미 저장된 주소입니다'만 보이고 두 버튼은 비활성
- 주소나 제목을 고치면 중복 표시는 사라지고 원래 [취소] [저장]으로 돌아간다

**저장 뒤**: **낙관적 업데이트는 하지 않는다**(2026-09-26 결정). id·추가 시각·빈 제목일 때의 도메인은 서버가 정하고, 409면 모달에서 골라야 하기 때문이다. 응답(약 150ms)을 받으면 캐시에 그 항목만 넣거나 바꾸고(목록을 다시 받지 않는다, 순서는 `orderLikeServer`) 모달을 닫는다.
- 저장 중에는 버튼을 모두 비활성, 실패(409 외)는 모달 안 버튼 위에 문구를 보이고 입력은 그대로 둔다

**키보드**: 처음 포커스는 추가면 주소 칸, 수정이면 제목 칸. Enter는 저장, Esc는 닫기(저장 중에는 무시). Tab은 모달 밖으로 나가지 않는다. 닫으면 연 버튼(또는 타일)으로 포커스를 돌려준다.
- 모달이 열린 동안 뒤 화면(상단바·그리드·상태바)은 `inert`. Tab 가두기만으로는 모달 안 빈 곳을 클릭해 포커스가 문서 맨 앞으로 간 뒤 Tab으로 뒤 타일에 닿았다(실제 앱에서 발견. Enter면 보이지 않는 타일이 열린다)
- 포커스는 inert가 풀린 뒤에 돌려준다(닫는 순간에는 아직 inert라 focus가 먹지 않는다)
